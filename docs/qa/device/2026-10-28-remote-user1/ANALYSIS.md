### 2. 主动扫描时钟 —— 机制活着，但**扫不到收银台**（本轮最大发现）

今天 0.0.101 段两次启动时钟，行为完全可解释但结果为空：

| 笔 | 时钟行为 | 关键测量 |
|---|---|---|
| 09:58 | 09:58:38 启动 → **10:01:46 超时停止（elapsed=187s）**，期间 110 轮只有 1 轮执行扫描（10:01:29，rootPkg=mm，16 字符帧 396 个 = 聊天/商品页，非成功页） | 时钟活着跑满 3 分钟 ✅ |
| 10:11:49 | 启动 → **10:14:34.595 停止（已离开支付环境，silentFor=164.7s）** —— lastSeenAt 从未刷新，110 轮零执行日志；20ms 后（10:14:34.614）通知通道解析到 2713 分 | 支付完成时刻 ≈ 10:14:30，时钟到最后一刻都没扫到收银台 |

**结论：HyperOS 2 的支付隔离比 v5 定案的更深一层 —— 不仅抑制事件，
收银台窗口在支付期间对 `rootInActiveWindow` 也不可见**（或可见但为空窗）。
主动扫描时钟每 1.5s 轮询一轮，110 轮全部扑空。

⚠️ **观测盲区**：`runProactivePaymentScan` 在「root 非支付包」或「root 是
支付包但窗口 0 字符」时**静默 reschedule 不打日志** —— 所以无法区分：
A) root 从不指向收银台；B) root 指向收银台但窗口全空（log4 支付宝 33 帧全
0 字符的同款）。两种可能修法不同（A 需扫窗口列表；B 需等窗口有文本后的
瞬间），下一版必须先把这个盲区填掉。

## 修复路线重估（待裁定）

1. **【新增·低成本高收益】解禁通知通道（修订 D-3）**：四份日志五台设备
   场景证明无障碍通道在 HyperOS 2 上不可靠，而通知通道 100% 命中。
   建议改为「无障碍证据为主、通知证据在无障碍 N 秒内未产出时兜底落卡
   （带 sourceType=notification 标记）」—— D-3 当年拒的是"纯通知落卡"
   的误报风险，可以用"无障碍首帧兜底确认 + 金额对账"收窄。
2. **【必做·观测】填掉主动扫描盲区**：每轮 rootPkg+文本长度节流日志
   （如 5s 一条），A/B 之争下一份日志立判。
3. **【待观测后定】窗口列表扫描**：`findPaymentResultRoots` 已有活动窗口
   收集，若 A 成立（root 不指收银台），把窗口列表里 mipay/收银台窗口的
   root 纳入扫描（对齐 v4 的 systemui 通道思路）。
4. **四问继续挂起**：等一笔「证据产出→门禁挂起」的日志，诊断轮设计才能
   发挥作用。
