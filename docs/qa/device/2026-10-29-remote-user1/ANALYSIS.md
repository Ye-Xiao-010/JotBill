# 远程用户 1 · 0.0.103(99) 验证日志分析（2026-10-28/29）

> 证据：`jotbill-diag-Xiaomi-20261028-223531.zip`（9268 行，跨 20:39–22:35，
> 含 0.0.102 与 0.0.103 两段会话）。meta：25019PNF3C / sdk36 / **0.0.103(99)**。
> 用户反馈：微信与支付宝支付均无弹窗，最后只收到通知。

## 结论先行

**0.0.103 的通知兜底（D-3 修订）按设计工作** —— 两笔支付全部落卡、通知全部送达。
**但无障碍通道这两笔都没能启动**，原因分两种：

| 支付 | 时刻 | 无障碍 | 通知兜底 | 弹窗 |
|---|---|---|---|---|
| 微信 32.00 元 | 20:39:17 | 零观察帧（**服务侧从未喂过 observation**） | ✅ 落卡 `pending-orphan-1` | 挂起 `OBSERVATION_STALE` → 30s 超时 → 仅通知 |
| 微信 3.75 元 | 22:31:15 | 零证据（**站内支付，root 一直是拼多多**） | ✅ 落卡 `pending-orphan-f` | **22:33:44 弹窗出现并被用户确认**（reason=SUCCESS 关闭，已入账） |

## 发现 1（关键可修）：拼多多站内微信支付的路由盲区

22:31 这笔支付的完整证据：

```
22:31:15.130 事件采样: pkg=pinduoduo(eventPkg=com.tencent.mm, rootPkg=com.xunmeng.pinduoduo)
22:31:17.080 结算页门禁: NOT_CHECKOUT_PAGE, class=com.tencent.mm.plugin.wallet_index.ui.orderhandlerui
             ← 这是微信支付 SDK 的 OrderHandlerUI，但被当作拼多多购物页处理
22:31:15.397 通知到达（8s 后通知兜底落卡）
```

**微信站内支付的窗口栈里，活动根窗口始终是拼多多**（微信只是事件包名/
叠加窗口），而 `resolveEffectiveShoppingPackage` 对此的归属规则是
`eventIsPayment && rootIsShopping → 返回 shopping 包`（防旧窗口残留误判，
2026-09 的修复）⇒ **支付观察管线从未启动**（主动扫描/窗口试探/词表扫描
全部没机会跑）⇒ 无障碍通道零证据，全靠通知兜底。

0.0.103 新增的试探路径本次**零触发**（`试探命中` 0 次、`窗口试探跳过` 0 次），
原因就是支付上下文根本没进入支付管线。这不是试探逻辑的问题。

## 发现 2：HyperOS 支付保护 133 秒全静默（含进程可能被冻结）

22:31:31.332 → 22:33:44.186 整份日志**零行输出 133 秒**（连 systemui 采样
都消失）——用户在完成微信支付的密码/确认环节。恢复后（22:33:44.186）
第一帧即触发 observation → 975ms 后弹窗出现（`PASS(age=669ms, foreground=pinduoduo)`）
→ 用户确认 → 22:33:49 `reason=SUCCESS` 关闭、冷却启动。

说明「最后收到通知」= 22:31:15 的 `待确认提醒`；弹窗在 133 秒静默结束后
才补上，用户已确认入账。

⚠️ 遗留疑点：22:31:15.4 落卡后、22:31:31 静默前的 16 秒里，overlay 管理
器**没有任何门禁日志**（不是 OBSERVATION_STALE 也不是 PASS）——下一版在
`processPendingChange` 入口与 `readPendingRow` 后各补一行日志，闭环归因。

## 发现 3：32 元那笔是「观察从未喂入」

20:39 卡的门禁：`OBSERVATION_STALE(age=1793191158111ms)` + `foreground=null`
—— age 是 epoch 时间戳（lastObservationAt=0 从未设置），即该会话里无障碍
服务从未向弹窗门禁喂过任何观察帧（服务未运行或该时段无白名单页面事件）。
挂起 30s 心跳 5 次后超时 → 仅通知。诊断轮的心跳/快照日志全部按设计落盘 ✅。

## 发现 4：支付宝零痕迹

全日志 `AlipayGphone` 0 次、支付宝通知 0 次。要么该笔发生在 133 秒静默内
（系统全抑制），要么用户未实际用支付宝支付（或支付宝通知被系统关掉）。
需向用户确认。

## 修复建议（按优先级）

1. **【主修】支付包事件的站内支付旁路**：`resolveEffectiveShoppingPackage`
   在 `eventIsPayment && rootIsShopping` 分支仍返回购物包以保旧窗口防误判，
   但这会把"站内支付"整段丢弃。建议：**保留返回值不变的同时，额外触发一次
   支付观察**（`observePaymentResultIfApplicable(event, eventPackage)`）——
   用 `includeWindows=true` 枚举窗口列表里的支付窗口 + 用 event.source
   子树试探。防误判由既有的结果页语义（词表/失败词/时效/转账）与去重链
   兜底。
2. **【观测】`processPendingChange` 入口/读行后补日志** —— 闭环发现 2 的
   16 秒疑点（下一份日志可判"coroutine 未跑 / 读行失败 / 主线程冻结"）。
3. **【确认】** 支付宝那笔是否真实发生、支付宝通知是否被系统关闭。

## 与 0.0.103 新特性的关系

窗口试探/主动扫描试探本次均未触发（支付管线没启动），因此**新特性本身
未被验证也未被否定**。发现 1 修复后，站内支付场景下支付管线才会启动，
试探路径才有机会在 HyperOS 静默期接管。
