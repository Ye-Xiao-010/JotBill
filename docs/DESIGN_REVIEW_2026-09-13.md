## R1｜"送 AI 唯一出口 = 支付成功信号"是过度简化 🔴

### 现状表述

- `G1-1` 的"严出"：**"送 AI"的唯一出口是检测到真实支付成功信号**
- `NEW_PROJECT_KICKOFF_V2.md 0.3.1 §7.6`：**"v1 只有一类合法触发源 —— 支付成功信号"**
- 该表述被 §7.6 表、FR-011/FR-015 等多处引用

### 代码实测：实际有 **4 条** AI 派发路径

| # | 路径 | 触发 | 消费哪个槽位 | 是否等支付成功信号 |
|---|---|---|---|---|
| 1 | **结果页主路径**（v1 新增） | 结果页文本解析成功 | **支付过程槽位**（结算页图） | ✅ 是（它就是触发源） |
| 2 | **结果页截图兜底** | 结果页**文本解析失败** ⇒ 现场截**结果页本身** | 付费侧截图 | ✅ 是（结果页可见即触发） |
| 3 | **断言通道（手动）** | **用户点击悬浮按钮** | `user-asserted:<pkg>` 专用槽位 | ❌ **否 —— 点击即派发** |
| 4 | **`USER_RETRY`（待确认中心重新识别）** | 用户显式点击 | 结算/重试槽位 | ❌ **否 —— 点击即派发** |

**路径 3 的代码实证**（`CheckoutAccessibilityService.kt`）：
```kotlin
storeResult = buffer.store(... captureTarget = USER_RETRY)     // :2695
...
val trigger = buffer.consumeForAi(                             // :2739  ← 直接消费，未经 coordinator
    slotId = slotId, intent = PurchaseIntent.USER_RETRY, pageFingerprint = pageFingerprint)
...
Log.i(TAG, "断言截图派发 AI: session=...")                       // :2754
val dispatched = dispatchReadyToAi(trigger)                    // :2755
```

**路径 2 的代码实证**：`maybeCapturePaymentResultScreenshot`（`:1654+`）在结果页文本解析失败时**现场截图并送 AI**，语义为 `SUCCESS_AI_UNVERIFIED`（**永不自动入账**）。

### 影响

若实现者按字面理解"**送 AI 必须等支付成功信号**"，并据此在派发入口加一道"必须有支付成功证据"的门禁 ⇒ **会同时打断路径 3 与路径 4**（用户点按钮后不再识别）**以及路径 2**（结果页文本解析失败 + 文本不可读时彻底无兜底）。

### 建议（低成本、不改行为）

把表述**按通道分列**，而不是给一个"唯一出口"的总括：

> **自动通道**：送 AI 的唯一触发 = **支付成功信号**（结果页文本解析成功，或文本不可读时的结果页截图兜底）。
> **手动通道**：送 AI 由**用户显式操作**触发（悬浮按钮断言 / 待确认中心重新识别），**不受支付成功信号约束** —— 用户的显式点击本身就是"该记一笔"的表达。

⇒ 需修改：`NEW_PROJECT_KICKOFF_V2.md` 0.3.1 的 §7.6 表述、`§2.3` 原则 2、`§11.2` FR-011/FR-015；`CONFLICT_REVIEW` 的 G1-1 "严出"条目亦宜加注"仅约束自动通道"。

## R2｜`IMPL_PLAN` §1.1 自身有错误 🔴

### 现状表述

`IMPL_PLAN_VERSION_B_2026-09-13.md §1.1`：
> **AI 只能经此入口派发**（`consumeForAi` 是唯一"图→请求"的出闸）… **不可另开旁路**

### 事实

**`consumeForAi` 有两个消费方**：
1. `IntentCoordinator.routeLocked`（`:460-464`）→ `deliver` → 服务回调 → `dispatchReadyToAi`
2. **`Service.performUserAssertedCapture`（`:2739`）直接调用 `consumeForAi`** → `dispatchReadyToAi`（`:2755`），**完全绕过 coordinator**（不经过门禁、不消耗 `attemptsBySession` 预算）

⇒ 方案 §1.1 的判断**不成立**。

### 影响

- 实现者可能误以为"改造只需动 coordinator"，从而**漏掉断言通道的适配**；
- 反向风险：有人为"统一出口"而**强行把断言通道改成走 coordinator** ⇒ 会引入断言通道本不需要的 `pageRole != CHECKOUT` 等门禁 ⇒ 破坏"用户断言绕过页面分类"的设计（G2.3 Q4）。

### 建议

- 更正 §1.1 为"**自动通道**的 AI 只能经 coordinator 派发"，并**明确断言通道是独立旁路且应保持独立**（这正是"保底"语义的实现方式）；
- 在方案中补一条**显式约束**：改造 A 的门禁放宽**只作用于 coordinator 路径**，**不得触及断言通道的独立派发**。

## R3｜90 秒 TTL 与设计自己的论证矛盾 🟠

### 现状

- **D-4 / G6.3 Q2a**：支付过程槽位 TTL = **90 秒**，起算点 = 搬入时刻（前台切换）
- **记录 G1-6 原文**（当时论证"槽位延长到 90s 方向正确"）：
  > 典型支付流程 5~30s，**慢的（输错重输/短信验证/换卡）可达 1~3 分钟**

### 矛盾

⇒ **设计的论证说"慢的可达 1~3 分钟"，却把上限定在 90 秒** ⇒ 恰恰在"输错重输 / 短信验证 / 换卡"这类**需要更多时间**的场景下图会过期。

### 影响（这是**最常见的失败模式**）

图过期 ⇒ 支付成功时支付过程槽位为空 ⇒ 走"立即落待确认"兜底 ⇒ 用户看到**金额正确但没有商户/分类**的待确认 ⇒ 每条都需手动补 ⇒ **自动化率显著低于预期**，且失败**集中在最需要用户耐心的场景**。

### 建议（三选一，需你裁决）

| 选项 | 做法 | 代价 |
|---|---|---|
| **甲** | **延长 TTL 至 3 分钟**（覆盖"慢的"场景） | 图在内存驻留更久；多订单并发上限略升 |
| **乙（推荐）** | **TTL 改为"直到支付结果页出现或会话过期（5 分钟）"** | 图的价值在"支付成功那一刻"最大化；用**事件**而非**固定时长**定义生命周期 ⇒ 与"起算点改为搬入时刻"同一思路（都是把生命周期绑定到**真实事件**而非拍数字） |
| **丙** | 维持 90s，接受降级 | 需在验收指标中明确"支付超 90s 的场景不计入自动化率" |

> **AI 推荐乙**：设计已经把起算点从"截图时刻"改成"搬入时刻"（事件驱动），TTL 也应一并事件驱动 —— 否则只是把"拍数字"从一处搬到另一处。**乙 还能顺带消除 D-4 遗留的"90s 待实测校准"**。

## R4｜`handoffContext` 单槽 ⇒ 多订单归属可能错配 🟠

### 现状

`IntentCoordinator.onEvent`（`:179-188`）：
```kotlin
if (isPaymentHandoff) {
    val retained = activeContext ?: handoffContext
    activeContext = null
    handoffContext = retained        // ← 单槽赋值，覆盖旧值
    ...
}
```

`handoffContext` 是**单一变量**，新交接会**覆盖**旧交接。

### 缺口

改造 B 解决了"**图**的隔离"（支付过程槽位 keyed by `sessionId`），但**"这一笔结果页属于哪一单"仍然依赖单槽 `handoffContext`**：

```
订单1 结算 → 交接（handoffContext = 订单1）
  → 用户返回购物 App，下订单2 → 交接（handoffContext = 订单2，订单1 被覆盖）
  → 用户先付完订单1 → 订单1 的结果页到达
  → 用 handoffContext（= 订单2）定位 ⇒ 指向订单2
```

**现有兜底**：`recordPaymentResultEvidence` 会经 `resolveSessionForPayment` 做"金额 + 时间窗 + 会话未占用"匹配；不匹配则 `NoMatch` ⇒ 孤儿待确认（**安全侧**）；多会话则 `Ambiguous` ⇒ 待确认（**安全侧**）。
**残留风险**：两单**金额相同**且时间接近时 ⇒ 可能误配到另一单的会话。金句仍是"**宁可重复一条待确认，不冒错账风险**"，但这不改变"**结果为错账**"的可能。

### 建议

| 选项 | 做法 |
|---|---|
| **甲** | 把 `handoffContext` 改为**按 sessionId 索引的映射**（`Map<sessionId, Context>`），结果页到达时按"金额 + 时间"在**多笔**候选中挑选 |
| **乙** | 保持单槽，但**显式记录"被覆盖的交接"**并在结果页到达时把被覆盖者一并纳入候选集 |
| **丙** | 维持现状，依赖 `Ambiguous` 安全侧兜底，**在文档中明确记为已知限制** |

> **AI 倾向甲**（与改造 B 的 sessionId 键控一致），但需注意：**结果页本身不携带订单号**（微信/支付宝结果页只有金额与商户），所以"挑选"本质上只能靠**金额 + 时间** ⇒ 甲能改善但不能根治。**若你判断多订单并发属低频场景，选丙并记为已知限制也是合理的。**

## R6｜需预期管理的设计代价（非缺陷）

1. **"详情页直达支付"场景搬入的是详情页图** —— 宽进的必然结果：AI 可能读到**未含最终金额/规格**的价格 ⇒ 与支付金额超容差 ⇒ 落待确认。这是"宽进换取不漏"的代价，需在验收指标中体现。
2. **多订单并发**（P3/M6）在版本 B 下仍是最脆弱形态 —— 改造 B/C 显著改善，但"结果页不带订单号"这一根本限制无法消除（见 R4）。
3. **AI 无法派发即落待确认** ⇒ 若某 App 搬运长期失效，待确认会**持续堆积**。建议为该原因（`PAYMENT_RESULT_AI_DISPATCH_UNAVAILABLE`）设置**量化日志与告警阈值**，避免静默劣化。

| **3** | **R4 多订单归属** | ✅ **采纳甲：映射化** —— `handoffContexts: Map<sessionId, Context>`，与支付过程槽位**同一键空间**；归属判定 **1 命中⇒用之 / 0 命中⇒孤儿待确认 / ≥2 命中⇒`Ambiguous`⇒待确认（安全侧）**；容量上限 4、随会话过期回收 | `IMPL_PLAN` **§2.5 改造 E（新增）**；与改造 B **必须同批实施** |

**裁定的理由（简述）**：
- **R1/R2**：纯表述修正，**不改行为、零代价**，但不改会让实现者按字面加门禁而**打断两条既有可用路径**（断言通道、结果页截图兜底）—— 风险与收益严重不对称。
- **R3 选乙而非甲（延长至 3 分钟）**：设计**已把起算点改为事件驱动**（搬入时刻），TTL 若仍是拍出来的秒数，只是把"拍数字"从一处挪到另一处；绑定"结果页或会话过期"才能让**生命周期跟随真实事件**，并**顺带消除 D-4 遗留的"90s 待实测校准"**。
- **R4 选甲而非丙**：丙（维持现状）的代价是"上下文**丢失**"⇒ 退到 `findRecentCheckoutReferenceForPayment`（取**最近活跃**会话）⇒ 这是**猜测**，可能误配；甲把同一情形变为"**可检测的歧义**"⇒ 落待确认（**安全侧**）。**甲严格更安全**，且与新槽位的 `sessionId` 键空间天然对齐。

**R4 的根本限制（不因甲而消除，已记为已知限制）**：微信/支付宝**支付结果页不携带订单号** ⇒ 归属只能靠 **金额 + 时间窗** ⇒ **同金额两单仍无法自动区分**。甲的价值是"**把丢失变成可检测的歧义**"，不是"让同金额两单能区分"。

**R5 / R6**：R5 已直接补入方案（宽进第二处配套）；R6 建议纳入验收指标，无需单独裁决。
