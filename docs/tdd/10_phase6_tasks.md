## 1. 文档使用规则

### 1.1 本阶段的执行对象

阶段六的工作对象是账单导入：微信/支付宝官方账单文件（CSV、XLSX、加密压缩包）的解析、预览、执行、撤销，以及跨来源核对与重复文件检测。

阶段五已经在实时链路（通知/结果页）上补齐了完整业务语义、字段优先级与多级去重，并为导入预留了两个挂点：`FieldPriorityResolver.Source.IMPORT`（7 级优先级第 3 级）与 `DuplicateGuard.checkLevel3`（导入记录标识查重）。阶段六把官方账单文件作为第二个数据来源接入同一套账本，做到"导入的账单与自动识别的账单同账本、同优先级、同去重框架"。

阶段六任务必须基于当前代码边界补齐或修正。不得因为设计文档列出某个类，就重复新建同职责类。开发开始前必须先检查目标类是否已存在，并在交接物中列出实际修改的类和原因。

### 1.2 角色定义

| 角色 | 责任 | 不得替代的角色 |
|---|---|---|
| 原生开发 | 修改 Kotlin、Android 配置和本地持久化边界内的实现，提供静态交接物 | 不得代替证据角色宣称真机通过 |
| RN/契约开发 | 只使用现有 `Native.d.ts` 方法和事件完成页面接入；契约缺口按 1.3 第 6 条走独立变更提交 | 不得自行新增未声明 Native 方法 |
| 契约审查 | 检查导入契约、类型、方法名、事件名和阶段边界 | 不得把代码存在误判为功能验收通过 |
| 证据角色 | 采集真机微信/支付宝官方账单导出文件（含密码压缩包）、元数据和证据索引 | 不得由开发对话兼任或用合成 CSV 替代官方样本 |
| 验收角色 | 按独立矩阵执行真机验收，记录通过、失败、未执行和阻塞 | 不得只根据开发自述填写通过 |

### 1.3 分支和提交规则

1. 每个任务从已确认的阶段六基线创建独立分支，分支名使用 `codex/phase6-<任务简称>`；不得在 `master` 或文档分支直接修改业务代码。阶段六代码基线为阶段五代码分支合并结果（当前为 `codex/phase5-t7-frontend-bridge`，合并到 `master` 后以 `master` 为准）。
2. 一个任务的代码提交只包含该任务的允许文件。审查修正必须在同一任务分支追加中文提交，不得把别的任务或证据文件混入。
3. 提交信息使用中文并包含任务编号，例如：`阶段六任务T3：接入微信账单适配器`。
4. 交接时必须写明：基线分支、基线提交、当前分支、提交哈希、修改文件、未修改但检查过的边界、未解决问题和下一角色。
5. 证据角色可以在专用证据分支提交样本或报告；验收角色必须引用证据提交哈希。开发提交不得包含真机账单原文（含真实姓名、卡号、交易对手），样本必须先脱敏。
6. 涉及 `docs/types/Native.d.ts` 的契约变更必须独立成提交并先经契约审查批准，不得与业务实现混在同一提交。

## 2. 阶段六范围与阶段七边界

### 2.1 阶段六允许交付

- 导入适配器（FR-040）：微信官方账单 CSV 与官方压缩包；支付宝官方账单 CSV、XLSX 与官方压缩包；UTF-8、UTF-8 BOM、GBK 编码；表头名称、列顺序与说明行变化的不同版本。
- 加密压缩包处理（FR-041）：密码只在当前导入过程中使用，不写入数据库、日志、剪贴板；解压文件存放应用私有临时目录，导入结束或取消后清理。
- 导入预览（FR-042）：正式写入前展示来源与格式版本、交易时间范围、总记录数与有效记录数、预计新增/合并/跳过/待确认/失败数量、类型分布。
- 导入执行与撤销（FR-043）：大文件分批解析；进度展示与安全取消；数据库事务写入；保存文件内容哈希与导入器版本避免重复导入；支持整批撤销最近导入，用户已修改记录受保护。
- 去重第 3 级启用（FR-060）：导入文件记录标识精确匹配，`DuplicateGuard.checkLevel3` 从占位改为实装。
- 字段优先级第 3 级启用（启动文档 5.4 节）：带官方交易号的导入字段以 `Source.IMPORT` 参与合并，高于 EVIDENCE、低于 RULE。
- 跨来源核对：导入记录与既有账单按订单号匹配时合并更新可变字段；按金额+时间窗口相似时计入"疑似重复"提示统计（沿用第 4 级口径，只提示不合并）。
- 导入批次管理：`ImportBatch` 实体记录文件哈希、来源、格式、导入器版本、状态与汇总计数（启动文档 10.5 节）。

## 3. 唯一 RN 契约与定义

### 3.1 `Native.d.ts` 是唯一公开契约

阶段六基线中与导入相关的已声明内容：

- `TransactionSource` 已包含 `'import'`；`ImportResult`、`CsvImportResult` 已定义。
- `Native.Backup.importData(filePath): Promise<ImportResult>` 已声明，原生端当前返回 `NOT_IMPLEMENTED`。

阶段六需要新增的契约（按 1.3 第 6 条流程，独立提交并经契约审查批准后由 T7 落地）：

```text
inspectImport(filePath: string, password?: string): Promise<ImportInspection>
executeImport(filePath: string, password?: string): Promise<ImportResult>   // 复用现有类型，补充 batchId 字段
undoImport(batchId: string): Promise<void>
getImportBatches(): Promise<ImportBatch[]>                                   // 撤销入口所需批次列表
```

`ImportInspection` 至少包含：来源（wechat/alipay）、格式（csv/xlsx/zip）、格式版本说明、文件哈希、是否重复文件、时间范围、总记录数、有效记录数、计划分类计数（新增/合并/跳过/待确认/失败）、类型分布、采样错误信息。精确字段以契约变更提交为准，本文只约束语义。

除上述方法外，阶段六不新增其他公开方法或事件；导入进度优先用返回值与轮询实现，若确需事件必须先立契约变更。

### 3.2 导入语义映射

官方账单行映射到既有 7 种 `TransactionType`，不新增类型值：

| 账单行特征 | 目标类型 | 语义说明 |
|---|---|---|
| 收/支 = 收入 | `income` | 正常收入 |
| 收/支 = 支出 | `expense` | 正常支出 |
| 收/支 = 不计收支 且 交易类型含 信用卡还款/花呗还款等 | `repayment` | 还款，不重复计入支出 |
| 收/支 = 不计收支 且 交易类型含 转账/零钱通/转入转出等 | `transfer` | 自有账户间转账 |
| 交易类型 = 退款/退回/返还（收入侧冲减） | `refund` | 冲减原支出 |
| 交易类型 = 手续费/服务费/提现费 | `fee` | 单独计支出 |
| 无法归入以上任何一类 | `adjustment` | 不计收支兜底，描述保留原文线索 |

### 3.3 导入路径与实时路径的账户差异

导入是历史数据回填，账户匹配失败是常态而非异常，与实时通知路径（不确定进待确认）不同：

- 账户推断只按"支付方式/交易对方文本 与 本地启用账户名 精确/双向包含匹配"，不做模糊猜测；复用阶段五账户匹配口径。
- 源账户匹配成功：填写 `accountId` 并按类型更新余额。
- 源账户匹配失败：`accountId` 置空入账，不更新余额，描述保留支付方式原文线索；计入预览"账户未匹配"提示，不进待确认。
- `transfer`/`repayment`：仅当源与目标账户都匹配成功才执行双账户余额更新；任一未匹配则只记账单不调余额。
- 进入待确认的唯一情形：行的语义本身无法安全判定（如解析出的类型与金额矛盾、退款无法关联且金额异常），数量应远小于账户未匹配。

### 3.4 去重与合并策略（导入路径）

| 检查 | 条件 | 命中行为 |
|---|---|---|
| 文件级查重 | 文件内容 SHA-256 已存在于 `ImportBatch` | 预览标记"重复文件"，默认拒绝执行，用户可强制 |
| 第 3 级（记录级，同源） | `(sourceType=import, importRecordId)` 已有账单 | 跳过，计入 skipped |
| 跨来源合并 | 行的官方交易号/订单号命中既有账单（任意 sourceType） | 不新建账单；可变字段以 `Source.IMPORT` 经 `FieldPriorityResolver` 合并更新，计入 merged |
| 第 4 级（相似提示） | 金额 + ±10 分钟窗口 + 账户/商户辅助因素 | 仅计入预览"疑似与现有账单重复"统计，不自动合并 |
| 无匹配 | — | 新建账单，计入 imported |

任何去重检查异常都按"跳过 + 错误记录"处理，不丢弃证据文件、不静默入账。退款不适用跨来源合并（沿用阶段五退款豁免：按退款单号去重）。

### 3.5 密码与临时文件安全（FR-041）

- 密码只通过方法参数在单次导入调用内使用；不写库、不写日志、不写剪贴板、不进崩溃上报；调用结束即解引用。
- 解压产物只写入应用私有缓存目录下的单次导入子目录；导入完成、取消、失败、异常路径都必须递归清理。
- 撤销与批次记录只保存文件哈希与计数，不保存账单文件内容或解压产物。

### 3.6 ImportBatch 状态机

```text
RUNNING -> COMPLETED          正常完成
RUNNING -> CANCELLED          用户取消（已写入部分必须清理）
RUNNING -> FAILED             解析或写入失败（同上清理）
COMPLETED -> UNDONE           整批撤销成功
UNDO_FAILED                   撤销存在受保护记录（部分撤销）
```

批次状态与账单计数在事务内同步更新；中断恢复时发现 `RUNNING` 且无对应进行中任务的批次，按失败处理并清理。

### 3.7 撤销语义（FR-043 与异常场景）

- 撤销范围：仅该批次新建的账单（以审计 `operator=batchId` 反查），以及该批次合并更新过的字段（按审计 old_value 回滚，仍受 3.8 保护）。
- 用户保护：导入后被用户编辑过（存在用户更新审计或 `field_locks` 非空）的账单不自动删除，逐笔列入"无法自动撤销"清单交用户处理。
- 余额恢复：删除账单走 `LedgerRepository` 既有反向余额调整，不引入第二套口径。
- 只允许撤销最近一批且状态为 `COMPLETED` 的批次；更早批次撤销留给后续阶段。

### 3.8 依赖决策

| 决策 | 选择 | 理由 |
|---|---|---|
| CSV 解析 | 原生 Kotlin 手写解析器 | 微信/支付宝 CSV 规整（引号包裹、无嵌套转义极端 case），避免第三方依赖；GBK/UTF-8 BOM 用 JDK Charset 原生支持 |
| XLSX 解析 | 原生轻量方案：XLSX 即 ZIP + XML，用 `java.util.zip` + `XmlPullParser` 读 sheet 与 sharedStrings | 避免 Apache POI 体积与方法数开销 |
| 加密 ZIP | 新增 `net.lingala.zip4j:zip4j`（Maven Central，Apache-2.0） | 官方导出压缩包为加密 ZIP，JDK 不支持解密；`react-native-zip-archive` 为 JS 侧能力且密码支持未验证 |
| 文件选择 | 复用 BackupModule SAF 模式（新请求码 + PendingKind.IMPORT） | 与现有导出/备份一致的 URI 生命周期管理，不新增 RN 依赖 |

若真机证据（T8）显示官方 ZIP 加密方式与 zip4j 不兼容，回退方案为换用支持的库并在契约不变前提下调整实现，属于实现细节修正，需在交接物中登记。

**依赖**：T1~T7 的审查提交和 T8 的主样本证据；需要明确设备、系统、微信/支付宝版本、存储条件。

**允许修改/新增文件**：

- `docs/qa/` 下的阶段六验收报告、测试矩阵和证据索引
- 验收角色的截图、UI dump、关键日志摘要和失败复现记录

**禁止触碰文件**：

- 不为通过验收修改业务源代码、契约或样本原文
- 不接入或验证银行短信、云端同步等阶段七及以后能力
- 不把开发分支的静态审查、构建结果或单元测试结果当作真机通过证据

**阶段六验收矩阵**：

| 场景 | 预期结果 | 必需证据 |
|---|---|---|
| 微信 CSV 导入（T8 主样本） | 预览统计正确，执行后账单入库，来源为 `import` | 批次 ID、计数截图 |
| 支付宝 CSV/XLSX 导入 | 同上 | 同上 |
| 加密压缩包导入（含密码） | 密码框出现、解压成功、临时目录清理 | 导入前后缓存目录列表 |
| 重复文件再次导入（改名） | 预览标记重复文件，默认阻止执行 | 预览截图 |
| 同记录二次导入 | 第 3 级命中，全部 skipped，无重复账单 | 两次执行结果对比 |
| 跨来源合并（订单号相同） | 不新建账单，可变字段按 IMPORT 优先级更新 | 字段前后对比 |
| 疑似重复统计（金额+时间窗口） | 预览计数含疑似重复，不自动合并 | 预览截图 |
| 不计收支行（转账/还款） | transfer/repayment 入库，不计收支，余额按 3.3 节口径 | 余额前后对比 |
| 退款行导入 | refund 入库并可关联原交易 | 关联记录 |
| 账户未匹配行 | 账号置空入账，余额不动，预览有提示 | 账单记录 |
| 大文件（≥1 万行）导入 | 30 秒内完成，进度可见，可取消 | 耗时记录 |
| 导入中取消 | 无半批残留，批次 CANCELLED | 批次状态、账单计数 |
| 整批撤销 | 批次账单删除、余额恢复、批次 UNDONE | 撤销前后余额对比 |
| 撤销含用户已修改记录 | 受保护记录保留，清单提示 | 保护清单 |
| 密码安全 | 日志/库/剪贴板无密码 | 日志检索记录 |
| 导入后备份/恢复 | 导入账单随备份恢复，来源不变 | 恢复后账单抽样 |

**验收报告必须逐项标记**：`通过`、`失败`、`未执行` 或 `阻塞`，并引用证据文件和提交哈希。未执行真机操作时，只能写"未执行"，不能写"通过"。

**提交要求**：中文提交信息 `阶段六任务T9：提交真机阶段六验收报告`；提交只允许的验收报告和证据索引，不得携带业务源代码或契约文件。

**交接产物**：按矩阵逐项标记的验收报告、设备/应用版本、证据文件清单、失败与阻塞说明、验收提交哈希和下一阶段交接事项。

## 6. 阶段六状态与交接示例

### 6.1 导入主链路

```text
用户在数据管理页点击"账单导入"
  -> SAF 选择文件（CSV/XLSX/ZIP）
  -> ImportFilePreparer：复制临时目录、流式哈希、类型/编码探测、（加密包）密码解压
  -> inspectImport：适配器解析（微信/支付宝）-> 预览统计（新增/合并/跳过/待确认/失败 + 类型分布 + 重复文件标记）
  -> 用户确认执行
  -> executeImport：RUNNING 批次落库 -> 分批事务写入
       每行：第 3 级查重（跳过）/ 跨来源订单号（合并，Source.IMPORT）/ 第 4 级（提示统计）/ 新建入账（余额按 3.3 节）
  -> COMPLETED：批次计数汇总，结果页展示，撤销入口可用
  -> undoImport（可选）：审计反查 -> 受保护记录除外整批回滚 -> UNDONE / UNDO_FAILED
```

### 6.2 不允许的捷径

- 跳过预览直接写库，或预览统计与执行结果口径不一致。
- 未知格式/未知版本强行解析入账，不报错。
- 导入字段直接覆写既有账单，不经 `FieldPriorityResolver`。
- 跨来源合并时连退款也按订单号合并（退款豁免）。
- 用"金额+时间接近"自动合并或丢弃导入行（第 4 级只提示）。
- 取消/失败后残留半批数据不清理。
- 密码写日志、入库或随批次持久化；解压产物留在临时目录。
- 撤销时删除用户已修改过的记录。
- 为了进度展示自行新增未声明事件或方法。
- 以手工构造 CSV 替代官方账单样本用于验收。

## 7. 证据、审查和完成定义

### 7.1 开发提交完成条件

开发任务只有在以下材料齐全时才可交给审查：

- 中文提交信息、分支名、基线提交和提交哈希。
- 允许/禁止文件清单与实际 `git diff --name-only` 一致。
- 导入契约、类型映射、去重分类、余额口径和安全要求的逐项对照表。
- 迁移脚本（T1）、依赖与许可证（T2）、版本兼容清单（T3/T4）、状态机与取消清理路径（T5/T6）按任务卡交付。
- 明确列出未运行的构建、测试和真机验证。

### 7.2 契约审查完成条件

契约审查必须至少检查：

- `TransactionType` 仍只有 7 个现有值；导入只映射既有类型。
- 契约变更独立提交且内容与 3.1 节一致；页面提交未再改契约；未批准前页面未引用新方法。
- `Source.IMPORT` 只在导入合并路径使用，优先级行为与 5.4 节一致；锁定字段不被覆盖。
- 去重第 3 级、跨来源合并、第 4 级提示行为与 3.4 节一致；退款豁免未丢失。
- 撤销保护边界与 3.7 节一致；余额恢复复用既有口径。
- 密码与临时文件处理满足 3.5 节；批次状态机与 3.6 节一致。
- 实际类复用当前实现边界，没有重复创建同职责类。

### 7.3 真机完成条件

真机完成只能由 T8/T9 角色根据独立证据签署。阶段六验收至少需要 4 个主样本证据、加密包密码安全证据、大文件性能与取消证据、整批撤销与保护证据、重复文件与跨来源合并证据。缺任何一项都必须标记为"部分完成"或"待验证"，不能从代码提交推断通过。

## 8. 风险与未解决问题

| 风险/问题 | 阶段六处理 | 责任角色 |
|---|---|---|
| 官方账单格式随版本变化（表头/列序/说明行） | 用 T8 真机样本调参；未知版本保持解析失败并记录，不强行入账 | 证据角色 + T3/T4 开发 |
| 加密 ZIP 算法与 zip4j 兼容性 | T2 静态验证 + T8 真机验证；不兼容则换库，契约不变 | T2 开发 |
| XLSX 轻量解析遇到合并单元格/多 sheet 变体 | 只读目标 sheet 与 sharedStrings，变体登记为已知限制；解析失败不入账 | T4 开发 |
| 大文件内存与性能（1 万行 < 30 秒） | 流式/分批策略（T5）；性能专项留阶段七 | T5 开发 |
| 跨来源订单号语义差异（同号不同义） | 合并仅更新可变字段且经优先级合并器；金额不一致计入冲突提示 | T5 开发 + 契约审查 |
| 导入记录海量账户未匹配 | 按 3.3 节置空入账不阻塞；预览提示数量 | T5 开发 |
| 阶段五代码尚未合并 master | 阶段六分支从阶段五最完整分支创建；合并顺序由项目负责人决定 | 契约审查 |
| 官方导出周期限制历史版本样本 | T8 标注"场景不可得"并用最近版本替代 | 证据角色 |
| 真机证据尚未采集 | 状态为"待验证"，由 T8/T9 独立推进 | 证据/验收角色 |

阶段六文档、代码审查或开发对话不得把阶段七能力包装为"回退""兼容""自动完成"。边界不清时，停止扩展并由契约审查创建后续阶段任务。
