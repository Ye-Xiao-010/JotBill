## 三、🔴 D-25 第二道去重被真机证伪

### 证据

```
10:05:45.908  支付结果页解析到证据: 金额=268分, SUCCESS, textLength=20
10:06:46.307  支付结果页解析到证据: 金额=268分, SUCCESS, textLength=20   ← 同一页面
```

数据库实表：

```
pending-orphan-044f32b  occurred_at=1790733945898  (10:05:45)
pending-orphan-bf77dd6  occurred_at=1790734006291  (10:06:46)
                       相差 60393 ms —— 比 60 秒窗多 393 毫秒
```

**用户在微信结果页停留超过 60 秒**（可能在看账单，或切走又回来），
同一页面被观测两次，两条都建了卡。

### 根因比"窗口小了"更深一层

三道防线的阈值**全部挤在 30~60 秒窄带内**，在同一刻集体失效：

| 防线 | 原阈值 | 60.393 秒时 |
|---|---|---|
| `markPaymentResultEvent` 事件记忆窗 | 60 秒 | ❌ 过期 |
| `sourceEventKey` 时间桶（`PaymentResultParser`） | 30 秒 | ❌ 跨桶 |
| **D-25 去重窗** | **60 秒** | ❌ **超 393 毫秒** |

**昨天定的 60 秒不是随手选的**——它来自「覆盖实测的 20 秒跨桶间隔 + 与事件记忆窗同口径 +
远小于 D-6 的 2 分钟」。每条依据都成立，但**没有一条考虑"用户在结果页停留超过 60 秒"**。
昨天的三笔里没有这个场景，所以定案看起来是对的。

### 处置

`PAYMENT_RESULT_EVENT_MEMORY_MILLIS` 与 `ORPHAN_DEDUP_WINDOW_MILLIS`
**同时调至 90 秒，且须保持同值**（不一致时先失效的那道形同虚设）。

90 秒的依据：覆盖实测的 60.393 秒；**仍远小于 D-6 的 2 分钟**（同额两单不得撞键）。

## 四、两个测试细节（都不是顺手写的）

### ① 新增真机回归用例，**判别力已实测验证**

`孤儿去重_真机实测60393毫秒的同一结果页重复观测只建一张卡`，
用真机原值 `1790733945898` / `1790734006291` 钉死该场景。

⚠️ **不是"算出来应该能红"，是真的红过**：

```
把 ORPHAN_DEDUP_WINDOW_MILLIS 临时改回 60_000L
  → 孤儿去重_真机实测60393毫秒… FAILED   （18 tests completed, 1 failed）
改回 90_000L
  → BUILD SUCCESSFUL，全量 411 / 0 failures
```

### ② 顺手发现原「超过 60 秒」负例会**假绿**

它原本用 `now + 90_000L` 当"窗口外"的值。窗口调到 90 秒后，该值**正好卡在边界上**
（`occurred_at BETWEEN ? AND ?` 两端闭区间 ⇒ 仍会去重）——**用它当负例，绿是假的**。

已改为 `now + 150_000L`：落在窗口外，且**仍在 D-6 的 2 分钟内**，
顺带证明了本窗口确实窄于 D-6。

## 七、踩的坑（今天新增 3 条）

11. ⚠️ **`settings put secure enabled_accessibility_services "<单个服务>"` 会抹掉用户其它无障碍服务。**
    本机列表有 5 个服务（小米AI阅读 / 支付宝 / GKD / omarea vtools / JotBill）。
    **昨天我这么写，等于替用户关了 4 个无障碍服务。**
    ⇒ 正确做法：**先读出完整列表、停进程、删文件、再把完整列表写回去**，
    由系统重绑自动拉起进程（这条昨天已踩，见下条）。
12. ⚠️ **无障碍重绑会*自动*拉起 App 进程**（昨天踩过，今天验证仍然成立）：
    "先启动 App 再删日志"是错的——`rm` 删掉的是刚建好的文件，进程句柄仍指向已删除的 inode，
    后续写入全进黑洞。现象：`init` 日志说"落盘已启用"，`ls` 却只有 dump 文件。
13. ⚠️ **`jotbill-dump.db` 只在 `Application.onCreate` 导出一次** —— 支付过程中不刷新。
    要看支付后的表内容必须重启 App。核对数据库时每轮都要重启，做 3 笔就重启了 3 次。

## 十、🔴🔴 挖到一个全新失败模式（比去重严重）

查 ¥55.90 这笔时发现了**完全不同**的问题。这笔**账单已经自动入账了**：

```
bill-9e0ed6380a2   5590   2026-09-30 10:29:04      ← 账单在账本里
checkout_sessions: 772aee2e  status=COMPLETED  journey_state=AUTO_COMMITTED  expires=10:33:54
```

完整时序：

```
10:28:53     会话创建
10:28:54     结算页稳定 CHECKOUT_STABLE
10:28:56     槽位搬入 + 交接登记 + 会话预写入
10:29:00.849 微信结果页解析出 ¥55.90
10:29:04     ★ AI 定论 → AUTO_COMMITTED → bill-9e0ed638 入账
10:29:31.873 证据落库（交接上下文）: Rejected(reason=PAYMENT_SESSION_CLOSED)   ← 会话已终态
10:29:31.874 支付结果归属 0 命中, pendingHandoffs=0                              ← 交接已被 AI 派发消费
10:29:31.866 落待确认 pending-orphan-b, reason=SUSPECTED_DUPLICATE             ← 又建卡
10:31:32.085 落待确认 pending-orphan-9, reason=SUSPECTED_DUPLICATE             ← 又建卡
```

### 这是「已入账 + 仍落待确认」并存

用户最终拿到的是：

- **1 条账单**（¥55.90，已自动入账）✅
- **2 条待确认提醒**（同一笔 ¥55.90）❌

`DuplicateGuard` **已经发现**了账单（所以两张卡的 `conflict_reason` 都是
`SUSPECTED_DUPLICATE,PAYMENT_RESULT_NO_MATCHING_SESSION`），
**但它只标记、不阻止建卡**。

⇒ 这正是 09-29 记录的「**识别了重复还照建**」，只是这次的"重复对象"从"另一条待确认"
变成了"**一条已入账的账单**"。

### ⚠️ 但不是资损

`PendingConfirmService.confirm` → `LedgerRepository.confirmPendingTransaction`
执行阶段五 T6 第 1 级去重，**命中会合并进既有账单、不产生第二笔**。
⇒ 用户点「确认」不会多出一笔 ¥55.90，只是**白做一次操作 + 账本里留一条多余记录**。

⚠️ 「白做一次操作」这句**未真机验证**——只读了代码（`confirmPendingTransaction` 的
去重第 1 级），**没有实际点过一次确认**。要下结论得在待确认中心点一下。

### 为什么交接会消失

`pendingHandoffs=0` 不是"交接没登记"——10:28:56.423 明确登记过。
是 **AI 派发成功时按"未占用"语义把交接上下文从映射里移除**了
（`CheckoutPurchaseIntentCoordinator`：`handoffContexts.remove(context.sessionId)`）。
而 AI 恰好在同一时刻定论并自动入账 ⇒ 结果页证据到达时，会话已 `COMPLETED`、
交接已消费 ⇒ 协调器无候选 ⇒ 落孤儿。

**这不是竞态 bug，是两条路径各自的正确行为撞在一起**：
- 路径一（AI + 结算页截图）：自动入账 ✅
- 路径二（结果页证据 + 归属判定）：会话已终态 ⇒ 转孤儿待确认 ✅

两条都对，合起来产出「账单 + 2 张待确认」。
