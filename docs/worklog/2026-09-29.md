## 三、关键发现（今天最有价值的部分）

### 发现 1：现象是「2 笔支付 → 5 条待确认」，根因有**两条**，不是一条

| 现象 | 根因 | 状态 |
|---|---|---|
| 归属判定恒 0 命中 | 结算页 `finalAmountMinor` 为 null | ✅ D-25 已修 |
| 同一笔落 2 条待确认 | 结果页事件键含 **30 秒时间桶**，跨桶即换幂等键 | ✅ D-25 已修 |

### 发现 2：**两笔支付、同一台设备、同一 APK，结果完全相反** —— 这是决定性对照

| | 第一笔 ¥19.90 | 第二笔 ¥17.99 |
|---|---|---|
| 结算页 `labeledTerms` | **`[]`** | **`[合计]`** |
| `finalAmountMinor` | **null** | **1799** |
| 归属判定 | **0 命中，`pendingHandoffs=1`** | 成功 |
| 最终去向 | 孤儿待确认 **×2** | **自动入账 `bill-ae5370cb3650a6f8`** |

**结论**：拼多多结算页的标签词**时有时无**。

- 不是"带标签通道在真机上根本不成立"（原假设 A）—— 是**这个页型本次渲染没出标签词**；
- 也不是"两个带标签金额确实不同"（原假设 B）—— 实测从未出现该样本；
- `unlabeled=[1990,2990,5190,760]` ⇒ 兜底 `singleOrNull()` 必然 null ⇒ **提取器的保守行为是正确的**。

⇒ **`PageAmountExtractor` 一行不动**（动它等于让提取器去猜），修法落在归属判定。

### 发现 3：一条**写在注释里的假设**失效了

`PAYMENT_EVIDENCE_MERGE_WINDOW_MILLIS` 的 KDoc 明写：

> 跨桶重复读由 `mergeSessionEvidence` 的 2 分钟收敛窗口兜底。

**该假设只对证据行成立**，收敛不到 `recordOrphanPaymentSignal` 独立新建的孤儿卡。

真机实测（同一 `sessionId=52c26818`）：

```
21:08:42.210 证据落库 Accepted(sessionId=52c26818, evidenceId=payment-2493…)  事件指纹 df4cec6593cb
21:08:42.219 落待确认 pending-orphan-2, reason=PAYMENT_RESULT_NO_MATCHING_SESSION, inserted=true
21:09:02.185 证据落库 Accepted(sessionId=52c26818, evidenceId=payment-2493…)  事件指纹 a63c2a56f9a3  ← 变了
21:09:02.190 落待确认 pending-orphan-4, reason=SUSPECTED_DUPLICATE, inserted=true   ← ★ 又建一条
```

- 证据层**完全正确**：两次都是 `payment-2493`，2 分钟窗口正常收敛；
- 跨桶算术：`1790687322157/30000 = 59689577`、`1790687342160/30000 = 59689578` ⇒ **相邻两桶**；
- 第二条**自己标了 `SUSPECTED_DUPLICATE` 却仍 `inserted=true`**
  ⇒ 不是"没识别重复"，是"**识别了还照建**"。这比原任务书设想的严重。

## 五、今天踩的坑（都踩过了，写下来是为了别再踩）

### 环境 / 工具类

1. **PowerShell `>` 重定向会损坏二进制** —— 拉 db 必须 `cmd /c "adb exec-out … > file"`。
2. **PowerShell 控制台输出中文是乱码** ⇒ **不要用控制台 grep 日志判断**，要 `adb pull` 到本地用工具读。
3. **`adb logcat -d -s <TAG>` 在本环境过滤不可靠** —— 用 `logcat -d | Select-String` 或拉文件。
4. **`adb shell am force-stop`** 会把应用置 stopped state，**连带停掉无障碍服务**。
5. **`settings put secure enabled_accessibility_services ""` 报 `Bad arguments`** —— 空串不被接受，那一步其实没生效。

### 时序竞态类（今天白跑过两轮）

6. ⚠️ **无障碍重绑会*自动*拉起 App 进程** —— 不必等 `monkey`。所以「先启动 App、再 `rm` 日志」是错的：
   `rm` 删掉的是刚建好的文件，进程持有的 `FileWriter` 句柄仍指向**已删除的 inode**，后续写入全进黑洞。
   现象极具迷惑性：`init` 日志明写"诊断日志落盘已启用"，`ls` 却只有 `jotbill-dump.db`（它落盘更晚，侥幸逃过）。
   ⇒ **正确顺序：让进程停住 → 删文件 → 拉起进程。**
7. **`adb logcat -c` 会把 `JotBillLog` 的 init 日志一起清掉** —— 以为清的是 logcat，实际诊断证据也没了。
8. ⚠️ **`logcat` 环形缓冲在本机只保留约 1~2 分钟**（实测 63032 行里最早一条是 21:00:54）。
   而一次支付从结果页落库到通知弹出要 20 秒、从打开购物 App 到支付完成要 2 分钟以上
   ⇒ **单靠 logcat 抓支付链路在时序上本来就不可靠。** 这条反过来印证了 `JotBillLog` 是这个场景该用的工具。

### 数据/资产类

9. **`jotbill-dump.db` 只在 `Application.onCreate` 导出一次** —— 支付过程中不刷新。要看支付后的表内容必须重启 App。
10. **`docs/showcase/` 56.9MB 从未入库** —— 与本次整理无关，但会持续污染 `git status`。
