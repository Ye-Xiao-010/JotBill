## 二、四条前提的核对结果

### ❌ 前提 1：「弹窗 UI 零耦合识别模块」——成立，但耦合点比预想的多一层

`PendingConfirmOverlayManager` 确实只订阅 `PendingChangeHub`，这点没错。
但**它还依赖无障碍服务主动喂帧级敏感状态**：

```kotlin
// CheckoutAccessibilityService:980（购物应用分支）
PendingConfirmOverlayManager.onObservationState(
    sensitive = observation.isSensitivePage, foregroundPackage = shoppingPackage)
// CheckoutAccessibilityService:1608（支付应用分支，observePaymentResultIfApplicable 内）
```

弹窗的 `canShowNow()` 要求 `lastObservationSensitive == false` **且**
`lastObservationAt` 在 30 秒内。精简版下 pending 由支付结果页产生，用户人在微信里，
所以支付分支那一处足以喂到帧 —— **侥幸成立，不是设计上成立**。如果将来把 pending
的产生时机挪回购物应用侧，弹窗会永远等不到非敏感帧。

### ❌ 前提 2：「`onAccessibilityEvent` 里两条并行分支，切得很干净」——不成立

实际是一个 100+ 行的单方法、多个提前返回。结算页链路**内联**在 `:983`–`:1022`，
且与必须保留的东西交织：

- `sensitivePageLatch.onShoppingObservation`（`:966`）
- `PendingConfirmOverlayManager.onObservationState`（`:980`）← 弹窗门禁
- `sensitivePageLatch.onUnobservableFrame`（`:886`）+ `dispatchOverlayInvalidation`

`observePaymentResultIfApplicable` 只在两个**支付包分支**里被调用（`:823`、`:925`），
不在顶层。所以门禁只能落在 `stabilityCoordinator.observe(...)` 这一行，
无法像伪代码那样包住整块。

### ⚠️ 前提 3：只 gate 结算页那条，达不到「日志中无截图 / 无 buffer.store / 无 AI 派发」

证据链路里还活着三条截图/AI 路径：

| 路径 | 动作 | 位置 |
|---|---|---|
| `maybeCapturePaymentResultScreenshot` | `takeScreenshot` → `client.recognizePaymentResult`（**外部视觉模型**） | 在证据链路内，4 个调用点 |
| `dispatchPaymentResultIntent` | `coordinator.trigger(PAYMENT_RESULT)` → 消费 `payment:<sessionId>` 槽位 → `dispatchReadyToAi` | 证据落库后 |
| `performUserAssertedCapture` | 悬浮按钮断言通道 `takeScreenshot` → `buffer.store` → AI | `:2745` |

第一条最要紧：**不 gate 它，"零截图"这条验收判据直接不成立。**
因此门禁从 1 处扩到 4 处（详见 `35bb10c`）。

`dispatchPaymentResultIntent` 那条**不需要**单独 gate：无槽位时它自然落到
`PAYMENT_RESULT_NO_MATCHING_SESSION` → 协调器孤儿出口 → `recordOrphanPaymentSignal`
落 pending —— 正是精简版想要的行为。这是意外收获，不是设计。

### ❌ 前提 4：「orphan 路径要写 pending 并关联 sessionId」——今天不成立

`CheckoutPaymentMatcher.kt:685`：

```kotlin
PendingTransactionEntity(candidateId = null, sessionId = null, ...)
```

orphan 卡**不带** sessionId。阶段一是纯新增，未改此处。
若这条不变量确实需要（影响退款/手续费的手动关联），得单独立项。

## 三、阶段二的前提也错了（较小）

「结算页识别关闭后 pending 的 `productDescription` 会为空 ⇒ 弹窗不显示商品描述」——
**弹窗从来没显示过 productDescription**：`pending_confirm_overlay.xml` 里没有对应
view，`PendingConfirmOverlayManager` 里零引用。这条天然成立。

所以阶段二改的是它周围真正会退化的两处：
1. **商户行**：精简版下商户只剩支付结果页文本解析一个来源。此前解析不出时固定显示
   "商户：未知"——读起来像"读到了但没看懂"，实际是"压根没有"；而这一行用户又不能改
   （弹窗只让改金额/分类/账户），是死路。改为空则整行 GONE。
2. **备注框**：hint 改为"买了什么？（可选）"，并预填 `productDescription`
   （`FeeExtractor` / 导入仍会写入，预填可避免信息凭空消失）。

已核实无需改动：`ReviewScreen.tsx` 已是条件渲染；`PendingReminderNotifier` 的通知正文
只有金额+类型+来源 → 验收 L6 不受影响。

## 四、七个提交里最需要盯的一处技术债

`applyCheckoutCaptureCapability()` 停用时复用
`checkoutCaptureOverlayManager?.onServiceInterrupted()` 收起悬浮按钮，
状态码落在 `SERVICE_NOT_CONNECTED`。

选它的理由：它是既有语义里唯一表达"按钮收起且不再可截图"的迁移，另造状态会污染
`CheckoutOverlayStatus` 契约与 RN 侧状态映射。**代价**是关掉开关后设置页可能显示
"服务未连接"，字面上误导。阶段二/三若要处理，应新增专属状态码而不是继续复用。
