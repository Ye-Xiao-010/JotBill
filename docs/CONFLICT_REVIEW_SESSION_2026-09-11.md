## G1 · 结算页认定

### G1-1｜结算页的定义（宽进）—— ✅ 已澄清

**AI 出题（陈述现状）**：

- 用户口语中的"结算页"= 商品详情页 / 购物车页；而文档 `NEW_PROJECT_KICKOFF_V2.md §7.5`（`:668-674`）明确写：`PRODUCT_DETAIL` 与 `CART` **不允许预捕获**，只有 `CHECKOUT`（订单确认页）可建立截图缓冲。
- 代码 `AccessibilityPageSummaryCollector.classifyPageRole`（`:533-578`）按 8 级短路分类，`PRODUCT_DETAIL` / `CART` 判出来后即被 `CheckoutPageDetector.detect`（`:118-120`）拒为 `NOT_CHECKOUT_PAGE`。

**用户裁定（原话要点）**：

> 商品详情页 / 购物车页面 / 更多的结算页是能作为我想法中的结算页，因为部分软件中商品详情页就能直接跳转到支付页（就是在微信/支付宝或其他付款方式的输入密码的页面）然后到支付结果页，这其中没有让用户确认的页面，但是有些软件又会存在这么一个确认的页面。所以这个结算页的定义会广泛一点，不然会造成部分应用的结算页无法捕获导致失败。

> 对于浏览行为，我的设计是，用户进入我们符合的页面就截图，但是只有我们检测到了真实的支付成功的信号才发送给 ai 让其识别，这样用户即使在浏览被截图，但是返回浏览另一个商品会再次截图替换掉在内存中的图片，保证发送给 ai 的是正确的支付行为所对应的结算图片。

**结论（设计意图）**：

1. **宽进严出**：
   - **宽进**——截图门槛放宽到"商品详情页 / 购物车页 / 订单确认页"三类，只要在支持 App 内命中即截图入内存。
   - ~~**严出**——"送 AI" 的唯一出口是**检测到真实支付成功信号**；截图本身不等于触发 AI。~~ → ⚠️ **0.3.2 修正（R1 通道分列）**：仅约束**自动通道**；**手动通道**（断言 / 重新识别）由用户显式点击触发、不受支付信号约束（G2.3 Q4 保底语义）。见 `NEW_PROJECT_KICKOFF_V2.md` §7.6 通道分列表。
2. **误截由"覆盖"消解**：内存只保留最新一张图，用户浏览别的商品会覆盖前一张，因此误截不构成问题。**关键防线在"送不送"，不在"截不截"。**
3. **设计动机**：部分 App 商品详情页直达支付密码页，中间无订单确认页；若只认订单确认页，这类 App 会**捕获不到 → 链路失败**。

**与现有实现的冲突**：

| 用户设计 | 现有文档/代码 | 冲突 |
|---|---|---|
| 商品详情页可截 | 文档 `§7.5`：`PRODUCT_DETAIL` 不允许预捕获 | 🔴 |
| 购物车页可截 | 文档 `§7.5`：`CART` 不允许（除非有最终订单字段） | 🟠 |
| 误截靠覆盖消解 | 代码靠**前置分类**阻止误截，无"覆盖即安全"的假设 | 🟠 |
| 截图与送 AI 解耦 | 代码中二者已解耦（`CHECKOUT_STABLE` vs 购买意图），方向一致 | ✅ |

### G2.4｜新问题：手动图与自动图并存时的覆盖语义 —— ✅ 已查明（含 1 项待裁定 → ✅ **D-16 已定案 B，见 G2.6**）

**用户提问（原话）**：
> 想到一个问题，那要是用户手动截图了但是后续有变动，代码识别成功让自动截图，这时候自动截图的是正确的需要覆盖用户手动的错误截图，这时候怎么办，能成功覆盖吗

**AI 实测回答：不会"覆盖",而是"并存"——且存在真实隐患。**

**事实 1｜同槽位内手动/自动是「两个独立候选」**（`CheckoutSnapshotBuffer:322-360`）
`SlotState` 分 `manualCandidate` 与 `automaticCandidate` 两个字段。写入规则 = **同类覆盖、异类并存**：
- 新的 `MANUAL_CAPTURE` → 只释放上一个 `manualCandidate`
- 新的 `CHECKOUT_STABLE` → 只释放上一个 `automaticCandidate`
⇒ **自动截图不会覆盖手动截图**；两者并存时标记 `requiresDisambiguation = true`（`:373`）。

**事实 2｜同指纹时自动被拒**（`:302-309`）
```kotlin
if (sameFingerprint.sourceReason == MANUAL_CAPTURE &&
    request.sourceReason == CHECKOUT_STABLE) return Rejected(MANUAL_CANDIDATE_PROTECTED)
```
⇒ 页面未变（指纹相同）时，手动图受保护、自动截图被拒。

**事实 3｜指纹不同时（用户场景）正常并存**
自动候选写入 `automaticCandidate`，与 `manualCandidate` 共存，不触发保护拒绝。

**⚠️ 真正的隐患在「消费端」**（`:681-698` + `:726`）
```kotlin
// 无指纹消费分支：手动优先
val manual = state.manualCandidate
if (manual != null && (manual.pageRole == CHECKOUT || intent == USER_RETRY)) manual
else candidates.singleOrNull() ?: Rejected(AMBIGUOUS_CANDIDATES)
...
releaseCandidates(state)     // ← 消费成功即释放该槽位【全部】候选
```
**叠加后果**：手动候选（过时/错误）+ 自动候选（正确）并存 → 消费时优先取手动 → 送 AI 的是过时错误图 → `releaseCandidates` 把**正确的自动图一并释放** → **正确的那张永远没机会被用**。⇒ **用户担心的情况真实存在。**

**两条缓冲**：
1. **带指纹消费可精确命中**（`findCandidate(state, fingerprint)`）——若意图指纹指向自动候选，消费的即正确图 ✅。但并存时 `resolveHandoffFingerprint`（`IntentCoordinator:533-558`）用 `candidates.singleOrNull()` 校正，**并存时返回 null ⇒ 无法校正**。
2. **两条手动路径影响完全不同**（⚠️ **术语已由 G2.7 修正**：二者并非"两个通道"，而是悬浮按钮点击后的**两条结局**）：

| 手动路径（G2.7 命名） | 写入槽位 | 对自动截图影响 |
|---|---|---|
| **路径 B：用户断言** | `user-asserted:<pkg>` **专用槽位** | **物理隔离，不影响** ✅ |
| **路径 A：会话绑定补截**（槽位已有自动候选时） | 与自动**同槽位** | 有上述风险 ⚠️ |

**重要提示｜现状"手动优先"是补丁而非原则**
注释（`:682-684`）自述：*"此前一律 `AMBIGUOUS_CANDIDATES` 拒绝，导致用户在自动候选之外手动补截一张后，支付交接反而消费不到任何快照"* ⇒ 该优先级是为**修"消费不到"的 bug** 而引入。
其名义依据"不变式第 5 条"原意是"规则命中不阻断**用户确认**"（讲**入账确认**），与"手动/自动截图谁更该用"**是两回事而被混用** ⇒ **该优先级可改**。

**待用户裁定（D-16）｜并存时谁优先？** —— ✅ **已定案：B（见 G2.6）**

| 选项 | 含义 | 代价 |
|---|---|---|
| **A（现状）** | 手动优先 | 可能送过时错误图，且正确自动图被一并释放 |
| **B** | 自动优先（用户期望："代码识别成功"更可靠） | 用户在槽位外补的更准的图反而被压住 |
| **C** | 不自动决断：并存 ⇒ `Ambiguous` ⇒ 落待确认让用户选 | 多一条待确认，但不错账（与 `ROADMAP §12` "宁可重复一条待确认，不冒错账风险"一致） |

**AI 倾向 C**（A/B 都会静默丢一张图；C 把选择权交用户，符合"严出"思路）。

> ⚠️ **该倾向已被后续撤回（2026-09-12）**：G2.5 查实 **C 不可行**（并存到不了 AI，退化为"手动优先 + 自动图被静默抹零"，比 A 更糟）；G2.6 定案 **B（自动优先 + 自动图被拒才回退手动）**。上表选项 C 的"落待确认让用户选"**建立在不成立的假设上**，不作实现依据。

| **无指纹**（`pageFingerprint == null`） | `Buffer:681-698` | 手动候选存在且（`pageRole==CHECKOUT` 或 `intent==USER_RETRY`）→ 取手动；否则 `candidates.singleOrNull()`，**并存时返回 null ⇒ `Rejected(AMBIGUOUS_CANDIDATES)`** |

⇒ **歧义到不了 AI 面前，"让 AI 处理两张图冲突"这条路不存在** ⇒ **C 方案不可行。AI 撤回上次的 C 倾向。**

#### 子问 ③ 待确认怎么显示？两条吗？—— **粒度 = 会话，不是截图**

**事实｜待确认 ID 由 sessionId 确定性生成**（`Matcher:1358`）
```kotlin

```
`upsertPendingForSession`（`Matcher:1844-1862`）按 ID **幂等 upsert**，非 append ⇒

**两种推论：**
- **同槽位（同 sessionId）**：两张图 → 一次派发 → 一条候选 → 最多**一条**待确认；显示的是**被送出去那张**（C/A 方案下即手动图）的信息，另一张从未参与。
- **两通道（不同 sessionId）**：→ **两条**待确认，各自独立。**根因不是"智能冲突"，而是通道未归并**（见 D-17）。

```kotlin
if (evidence.any { it.indicatesPaidOutcome() }) return false          // :1340 已有支付成功证据 → 不落待确认
```
⇒ 手动断言仅在"**无支付证据且未入账**"时才落待确认。一旦自动通道拿到真实支付结果并匹配成功，断言那条待确认不会被创建 / 会被自动入账路径删除（注释 `:1323`）。
⇒ **但删除是按 sessionId 的** ⇒ **两通道 sessionId 不同则删不掉对方** ⇒ 仍可能双条。

⇒ 真实答案是：**AI 根本遇不到这个场景 —— 缓冲区在它上游就把分岔做完了**。

#### 核对 2｜候选层面：**存在一处不对称** ⚠️

`Buffer.store:302-309`：
```kotlin

    request.sourceReason == CHECKOUT_STABLE) return Rejected(MANUAL_CANDIDATE_PROTECTED)
```
| 方向 | 代码行为 | 是否符合边界原则 |
|---|---|---|
| 手动 → 自动 | 换页时不清理自动候选（`SnapshotCoordinator:1089`） | ✅ 自动不受手动干扰 |
| **自动 → 手动** | **同指纹时自动被拒**（`MANUAL_CANDIDATE_PROTECTED`） | ⚠️ **自动被手动干扰** |

**关键在「同指纹」条件**：指纹相同 ⇒ **用户手动截图后页面根本没变** ⇒ **自动通道同样判得出这一页**（否则指纹不会相同）。按用户原则，**此时该由自动上，手动的存在已无必要**，但代码反向拒绝了自动。

⇒ **严格表述**：**自动不会干扰手动（✅ 已由代码保证）；但手动会干扰自动（⚠️ 仅限同指纹）**。该不对称是"手动优先是补丁而非原则"留下的痕迹——保护从"手动截完别忘了它"的修补角度加入，未反问"这一页自动明明认得，还需要手动吗"。

#### 三场景对照

| 场景 | 自动认得出吗 | 原则下该谁上 | 代码实际 |
|---|---|---|---|
| 商品详情页直达支付（无订单确认页） | 认得出 | 自动 | 自动 ✅ |
| 代码判不了的页面（非标页面/结构异常） | **判不出** | **手动** | 手动 ✅（断言通道绕过分类） |
| 结算页手动补截 + 同页自动截图 | 认得出 | 自动（手动无必要） | **自动被拒** ⚠️ |

⇒ 前两场景完美符合；**第三行是唯一不一致**，构成 D-16 的实施细化项（下条）。

#### D-16 实施细化（并入代码评估清单）

按 B 定案，需改三处：

### G3.3｜断言通道与自动通道的 sessionId 归并 —— ✅ **已裁定：不归并**

#### 术语澄清（避免"通道"一词再被误读）

"两通道"这一命名**由 AI 所起，指代的是「写数据的路径」，不是「手动与自动」**：

| AI 命名 | 实际路径 | 槽位 | 触发者 |
|---|---|---|---|
| **断言通道** | `performUserAssertedCapture`（`Service:2543-2607`）→ 立即送 AI | `user-asserted:<pkg>` **专用槽位** | **手动**（悬浮按钮） |
| **自动通道**（AI 曾称"会话通道"） | `handleStable` → 结算槽位 | 结算槽位 | **自动**（系统观察） |

⇒ 二者恰为"一手动、一自动"，但**本质区别在写哪个槽位**，而 `sessionId` 是**跟着槽位走**的（`SlotState.sessionId` 为 `val`，`Buffer:217-225`）。

#### 问题成因

| 环节 | 事实 | 位置 |
|---|---|---|
| 断言通道 sessionId | `CheckoutRequestKey.newSessionId()`——**每次点按钮都是全新 UUID** | `Service:2678` |
| 自动通道 sessionId | 槽位建立时生成，同一结算过程内复用 | `Buffer:295-300` |
| 待确认 ID | `stableId("pending", session.id)` ⇒ **一个 sessionId 一条** | `Matcher:1358` |
| ⇒ 后果 | 两条路 sessionId 不同 ⇒ **同一次支付可能出现两条待确认** | — |

#### 裁定依据

用户 G2.3 Q4 原话：
> 手动的目的是让用户来做**最后的保底截图**……有些页面我们的代码是不能知道这个页面该不该截图的。

⇒ **手动 = 用户主动表达"这一笔我要记"**，其语义与自动通道的"系统识别到一次支付"是**两个不同来源的记录，不是重复**。

| 记录 | 代表 | 是否重复 |
|---|---|---|
| 自动通道那条 | 系统识别到的一次支付 | 系统视角 |
| 断言通道那条 | **用户主动要求记的一笔** | **用户视角** |

**强行归并的风险**：会出现"用户明明点了，却因系统已有一条而被吞掉"的倒退——这与"保底"的设计初衷直接冲突。

⇒ **结论：不归并，两条独立保留。不需代码改动。** 若将来希望减少困惑，可在待确认中心**做视觉关联提示**（非合并），属 UI 增强项，不在本次范围。

### G4.4｜容差数值 —— ✅ **已裁定：选项 B**

**用户裁定（原话）**：

⇒ **容差 = `max(¥1.00, 支付金额 × 5%)`**

**精确定义**（金额单位 = 分）：

```kotlin
val toleranceMinor = maxOf(100L, evidence.amountMinor * 5 / 100)   // ¥1.00 与 5% 取大
val withinTolerance = abs(candidate.amountMinor - evidence.amountMinor) <= toleranceMinor
```

| 项 | 值 | 依据 |
|---|---|---|
| 绝对下限 | `¥1.00`（100 分） | 保证小额单有基本余量（运费固定型差异） |
| 比例项 | 支付金额 `× 5%` | 自适应大额单（优惠/手续费等比例型差异） |
| 取值规则 | **两者取大** | 小额时下限兜底，大额时比例放宽 |
| 超出处理 | 保留冲突原因 ⇒ **转待确认** | 与"准确优先于自动化率"原则一致 |
| 入账金额 | **以支付金额（`evidence.amountMinor`）为准** | 支付金额是事实，AI 读的是页面 |
| 常量性质 | **可调常量** | 待真机数据校准（与 D-4 的 90s、D-7 的窗口同一处理方式） |

**曾被排除的方案**：
- A（纯绝对 `±0.01 元`）：过紧 ⇒ 正常优惠/运费单全部进待确认；
- C（纯绝对 `±¥1.00`）：大额偏紧（1000 元单仅容忍 1 元），无法容纳比例型差异。

**配套代码改动（已定案）**：
- `CheckoutPaymentMatcher.evaluate:1995-2009` 金额分支由单边不等式改为：
  `abs(candidate.amountMinor - evidence.amountMinor) <= maxOf(100L, evidence.amountMinor * 5 / 100)`；
- 超出容差 ⇒ 保留冲突原因（如 `AI_AMOUNT_DIFFERS_FROM_PAYMENT`）⇒ 进入待确认；

### G7.2｜D-22：结果页落库顺序（决策点 4 = ②）—— ✅ 已裁定

**问题实质**：支付成功后，「创建待确认 + 弹窗」与「向 AI 派发截图」谁先谁后。

**被否决的 ①（现状语义）**：证据落库时**同一事务内创建待确认** ⇒ 弹窗立即触发，而 AI 尚未派发 ⇒ 弹窗内容为空；AI 返回无冲突后自动入账并清理该待确认 ⇒ **"弹窗未及操作即被核销"**。

**裁定 ②**：**证据仍立即持久化**（不丢），但**不创建待确认**；先派 AI；AI 返回后按结果决策：

| AI 定论 | 动作 |
|---|---|
| 无冲突 | **静默自动入账，全程不弹窗** |
| 有冲突 / 字段缺失 | 才落待确认 ⇒ 弹窗（**此时信息完整**） |
| 失败 / 超时（32s） | 落待确认 ⇒ 弹窗（0 金额时按 **D-21** 要求补金额） |
| （AI 无法派发：槽位空 / 超预算 / 未配置） | **立即落待确认** ⇒ 弹窗，**不静默** |

**关键澄清**：**两个选项都不会丢证据** —— 差别只在"**待确认与弹窗**"这个面向用户的动作何时发生，不在"证据是否立即写库"（两者都立即写）。

**实现要点（方案 §2.4 详述）**：
- **核心动作仅一条**：把 `pendingFromEvidenceOnly()` 的调用**从"证据落库时"推迟到"AI 定论为需 review 时"**；
- **无需新增状态**：`WAITING_ENRICHMENT` **本身已是"等待 AI 定论"的显式中间态**，且已持久化在 Room ⇒ **进程被杀可恢复**（原担心的"需要显式状态"自然满足）；
- **两条兜底必须实现**：① AI 超时（32s）⇒ 走现有 `AI_RECOGNITION_FAILED` 路径落待确认；② **新增启动期兜底扫描**：`WAITING_ENRICHMENT` 且无 AI 结果的会话 ⇒ 落待确认。

**连带效果**：
- **修复 P5**（弹窗过早 / 内容不全 / 自消失）；
- 缓解 **P18**（`WAITING_ENRICHMENT` 获得明确退出路径），但 P18 的 `ignore` 语义仍待单独确认；
- **P19**（弹窗不自动撤下）紧迫性下降，但仍应补 `removed` 分支。
