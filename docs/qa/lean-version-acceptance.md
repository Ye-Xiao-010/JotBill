## 一、验收标准（7 条）

### L1 · 支付完成 → 弹窗出现（唯一核心指标）

**操作**：拼多多 → 结算页 → 提交订单 → 微信/支付宝支付 → 输密码 → 支付结果页。
连续 20 笔，全程自然使用（不要刻意加速或卡点）。

**通过判定**：**命中率 ≥ 90%（20 笔中 ≥ 18 笔）**，其中**「即时命中」≥ 70%（≥ 14 笔）**。

> ⚠️ 本条判据于 2026-10-12 依真机实测改写过一次，改动原因见下方「判据改写记录」。
> 改写**放宽**了原始意图（"弹窗出现在支付成功页"），放宽幅度与原因均已写明，
> 不得当作"原始判据已达成"。

#### 命中 = 两个层级（都必须记录）

| 层级 | 判定 | 日志特征 | 用户可见行为 |
|---|---|---|---|
| **A 即时命中** | 门禁 `PASS` | `弹窗门禁判定: allowed=true, reason=PASS(age=..., foreground=<支付包>)` 紧跟 `付款确认弹窗已显示` | 弹窗**在支付成功页上**出现 |
| **B 延迟命中** | 门禁 `NO_OVERLAY_PERMISSION` 后放行 | `弹窗候选挂起等待非敏感帧` → `弹窗候选挂起后放行: waitedMs=..., reason=PASS(... foreground=<非支付包>)` → `付款确认弹窗已显示` | 弹窗**延迟数秒、且需离开支付应用后**才出现 |

**统计口径**：A + B 计入「命中率 ≥ 90%」；仅 A 计入「即时命中 ≥ 70%」。
两者都要按平台（微信 / 支付宝）分列。

> B 档不算 bug，但也**不能算达成原始意图** —— 用户在支付成功页上并没有看到弹窗。
> 它的存在本身就是「弹窗未绑定支付成功页」这一架构问题的可观测证据，
> 详见 `ISSUE_2026-10-10_lean_payment_overlay_popup_timing.md` 根因 A。

#### miss 的判据与归因（每笔 miss 必须归到下面一类，否则视为不可解释故障）

| miss 形态 | 日志特征 | 归因 |
|---|---|---|
| 无证据 | `支付结果页未生成成功证据: reason=...` 或 `支付结果页无可用节点树` | 结果页文本解析失败 —— **精简版的主要损失面** |
| 证据有、弹窗没出 | 有 `pending变更事件` 但无 `付款确认弹窗已显示` | 弹窗门禁挡住，见下方三行 |
| **候选超时（15 秒悬崖）** | `弹窗候选挂起等待非敏感帧` 后**再无** `弹窗候选挂起后放行`，等 ≥15s | `PendingPromptPolicy.CANDIDATE_TTL_MILLIS = 15_000L`。用户在支付宝成功页停留超 15 秒 ⇒ 候选作废 ⇒ **该笔永久无弹窗**（仅系统通知兜底）。**这是最严重的一类 miss，单独计数** |
| 弹窗候选挂起（未超时） | `弹窗候选挂起等待非敏感帧` → 随后 `弹窗候选挂起后放行` | 帧级敏感门禁，属 B 档而非 miss |
| 被策略跳过 | `弹窗跳过: <reason>` | 去重窗口 / 免打扰，见 `PendingPromptPolicy` |
| 被去重吃掉 | `支付结果页同一事件已处理，跳过重复解析` 或 `孤立支付证据判为重复观测` | **不算 miss**，同一笔只应出一张卡 |

> 同额连续支付的判据（2026-10-24 用户裁定后）：
> **同包同额、且页面文本哈希一致、且间隔 ≤15 秒** ⇒ 判为同一笔，合并；
> 超过 15 秒或文本哈希不同 ⇒ 各自建卡。
> 跑 20 笔时**金额仍建议各不相同** —— 否则测的是"同额判据"而不是弹窗命中，
> 一笔 miss 会被误归因成"被合并"。

#### 记录表（每笔一行，20 笔填满）

| # | 金额 | 平台 | 结果页日志 | 门禁 reason | 弹窗层级 | waitedMs | 归因 |
|---|---|---|---|---|---|---|---|
| 1 | | | | | | | |
| … | | | | | | | |
| 20 | | | | | | | |

（`waitedMs` 仅 B 档填写，来源为 `弹窗候选挂起后放行` 那一行。）

#### 判据改写记录（2026-10-12）

**原始判据**：命中 = "弹窗出现在支付成功页"。唯一判据关键词
`付款确认弹窗已显示` 只验"这张卡有没有弹出来"，验不出"弹在哪一页"。

**实测结论**（真机 25128PNA1C / Android 17 / MIUI-HyperOS，两轮共 4 笔）：

| 平台 | 门禁 reason | 实测延迟 | 放行时前台 | 层级 |
|---|---|---|---|---|
| 微信 | `PASS(age=2ms)` | 360ms | `com.tencent.mm`（仍在支付成功页） | **A** |
| 支付宝 | `NO_OVERLAY_PERMISSION` | 3.7s / 4.0s | `com.xunmeng.pinduoduo`（**已离开支付宝**） | **B** |

**根因**：MIUI 在应用进入后台后会短暂收回 `SYSTEM_ALERT_WINDOW` 权限
（实测系统日志 `SYSTEM_ALERT_WINDOW ... duration=3s` / `57s`），JotBill 的弹窗门禁
读 `Settings.canDrawOverlays()` 为 false 而挂起候选。微信支付路径不经过同一段后台
切换窗口，支付宝经过，所以被挡。**这是稳定复现，不是偶发**（两轮 4 笔全部如此）。

**改写理由**：A/B 两档都必须承认，否则会出现两种坏结果之一 ——
① 拿"弹窗出现过"当"弹窗在支付成功页出现"，把架构缺陷记成通过；
② 把 B 档一律记成 miss，掩盖"用户确实看到了弹窗、只是晚了"这个真实收益。
分档 + 双阈值是唯一不撒谎的写法。

**本次样本量：2 笔（A 1 / B 1），不足以判定任一阈值。L1 正式 20 笔尚未执行。**

### L2 · 弹窗内改金额 / 分类 / 账户 → 入账成功

**操作**：L1 中任意一笔命中后，在弹窗里改金额、换一个分类、换一个账户，点"确认入账"。

**通过判定**：
- 日志出现 `付款确认弹窗已关闭: reason=SUCCESS`
- 账单列表出现该笔，`amountMinor` / `categoryId` / `accountId` 与弹窗内选择一致
- 备注框内容写进账单的 `description`
- 待确认中心该条目消失

**同时验证就绪判据**：清空金额 → "确认入账"按钮必须置灰（`PendingConfirmReadiness`）；
不选分类或不选账户同样置灰。

### L3 · App 内手动记账正常

**操作**：不经过任何自动识别，在 App 内手动新增一笔支出。

**通过判定**：入账成功，金额/分类/账户/备注均正确；账单与余额同步更新。

**注意**：这条与识别链路完全解耦，**用于排除本次改造误伤了通用入账路径**。

### L4 · AI 对话记账正常

**操作**：设置页配置 AI 模型 key，在 AI 对话里说"帮我记一笔 35 块买咖啡"。

**通过判定**：AI 解析出金额与分类 → 入账成功，账单可查到。

**注意**：AI 对话是精简版保留的三条入口之一，与被砍的"结算页截图 AI 识别"
是**两回事**，不要混淆。本次改造不应影响它。

### L5 · 密码页零弹窗零截图

**操作**：在微信支付密码输入页**停留 10 秒以上**（含多次进出密码页）。

**通过判定**（两条同时成立）：
- **零弹窗**：无 `付款确认弹窗已显示`
- **零截图**：无 `结算页 AI 派发`、无 `候选已写入`、无 `支付结果页截图兜底已取得`

**旁证**：应出现 `支付结果页截图兜底已禁止: 结算页截图识别链路已停用`（或敏感页原因）
—— 说明兜底路径确实被触达并拒绝了，而不是压根没跑。

> 这条**不依赖能力开关**：`sensitivePageLatch` 是密码页零截图的不变式依据，
> 阶段一切换开关时**刻意没有清理它**（清理只会让截图更少，不构成放宽风险）。

---

### L6 · 无障碍未启用时 → 通知兜底可见

**操作**：在系统设置里关掉无障碍服务，然后完成一笔支付（或用任意方式产生一条待确认）。

**通过判定**：
- 无 `付款确认弹窗已显示`（弹窗的帧级门禁依赖无障碍喂入观察帧，无服务时不弹 —— **这是正确行为**）
- **系统通知出现**，标题"有一笔交易待确认"，正文含金额
- 待确认中心里该条目可见

> 通知正文只由「金额 + 类型 + 来源」构成，不依赖商户或商品描述，
> 因此阶段二改动不影响这条。

### L7 · MIUI 假死 / 被杀后重绑，弹窗恢复

**操作**（沿用 `golden-path-regression.md` §一 的假死检查法）：

```powershell
adb shell settings get secure enabled_accessibility_services   # 记为 $cur
$svc = "com.jotbill.app/com.jotbill.app.recognition.CheckoutAccessibilityService"
# 先摘后挂，强制重绑
adb shell settings put secure enabled_accessibility_services ($cur -replace [regex]::Escape($svc), "")
Start-Sleep 3
adb shell settings put secure enabled_accessibility_services $cur
adb shell settings put secure accessibility_enabled 1
```

随后再完成一笔支付。

**通过判定**：
- 重绑后日志出现 `结算页无障碍观察服务已连接`
- 该笔支付仍能弹出确认弹窗（L1 口径）
- 未重绑而服务假死时，表现为**零 `无障碍事件采样` 日志** —— 与代码无关，是 MIUI 已知问题

## 二、不再要求的部分（明确退役）

以下项目在精简版**不再作为验收标准**，原因是它们测的路径已被开关停用或已不是本版本的目标：

| 退役项 | 原出处 | 退役原因 |
|---|---|---|
| G1 拼多多+微信全链路（结算页稳定→截图→AI 证据→自动入账） | `golden-path-regression.md` §三 | 结算页稳定帧监测已停用，自动入账链路不可达 |
| G2 京东弹窗结算页 | 同上 | 同上 |
| G3-1 已捕获状态手动重截 | 同上 | 无自动候选可"顶替" |
| G3-2 自动截图进行中抢占 | 同上 | 无自动截图，无抢占时序 |
| G3-3 识别失败页用户断言 | 同上 | 断言通道即截图通道，已停用 |
| N2 非结算页不建会话 | 同上 §四 | 无 `ensureSession` 调用 |
| N4 AI 未验证证据只进待确认 | 同上 | 结算页 AI 已停用，不产生未验证证据 |
| **结算页自动入账率** | ROADMAP 第十节 | 本版本不追求自动入账；入账一律经用户显式确认 |

**保留不退役**：N1（密码页零截图）→ 升格为 L5，且判定更严（要求同时零弹窗）。

## 三、通过标准

- **L1 必须达标**：命中率 ≥ 90%（A 即时 + B 延迟），**且**即时命中 ≥ 70%。
  这是本版本唯一的一票否决项。B 档占比不设上限，但**必须在验收报告里按平台列出**——
  支付宝走 B 档说明「弹窗未绑定支付成功页」这个架构问题仍然存在，
  不能因为"用户看到了弹窗"就当它已解决。
- L2–L7 为地板项：任一条失败 = 本版本有回归，需修复后重跑。
- 任一条失败时，**先确认能力开关状态**（见 §零），再判断是不是本次改造引入的问题。
- 精简版**不合并 main**。完整自动记账能力仍由 `usable-0.0.98-full-auto` 承载，
  那条分支继续按 `golden-path-regression.md` 验收。
