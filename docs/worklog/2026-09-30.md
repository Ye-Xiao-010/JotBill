## 三、🔴 D-25 第二道去重被真机证伪

### 证据

```
10:05:45.908  支付结果页解析到证据: 金额=268分, SUCCESS, textLength=20
10:06:46.307  支付结果页解析到证据: 金额=268分, SUCCESS, textLength=20   ← 同一页面
```

数据库实表：

```
pending-orphan-044f32b  occurred_at=1790733945898  (10:05:45)
pending-orphan-bf77dd6  occurred_at=1790734006291  (10:06:46)
                       相差 60393 ms —— 比 60 秒窗多 393 毫秒
```

**用户在微信结果页停留超过 60 秒**（可能在看账单，或切走又回来），
同一页面被观测两次，两条都建了卡。

### 根因比"窗口小了"更深一层

三道防线的阈值**全部挤在 30~60 秒窄带内**，在同一刻集体失效：

| 防线 | 原阈值 | 60.393 秒时 |
|---|---|---|
| `markPaymentResultEvent` 事件记忆窗 | 60 秒 | ❌ 过期 |
| `sourceEventKey` 时间桶（`PaymentResultParser`） | 30 秒 | ❌ 跨桶 |
| **D-25 去重窗** | **60 秒** | ❌ **超 393 毫秒** |

**昨天定的 60 秒不是随手选的**——它来自「覆盖实测的 20 秒跨桶间隔 + 与事件记忆窗同口径 +
远小于 D-6 的 2 分钟」。每条依据都成立，但**没有一条考虑"用户在结果页停留超过 60 秒"**。
昨天的三笔里没有这个场景，所以定案看起来是对的。

### 处置

`PAYMENT_RESULT_EVENT_MEMORY_MILLIS` 与 `ORPHAN_DEDUP_WINDOW_MILLIS`
**同时调至 90 秒，且须保持同值**（不一致时先失效的那道形同虚设）。

90 秒的依据：覆盖实测的 60.393 秒；**仍远小于 D-6 的 2 分钟**（同额两单不得撞键）。

## 四、两个测试细节（都不是顺手写的）

### ① 新增真机回归用例，**判别力已实测验证**

`孤儿去重_真机实测60393毫秒的同一结果页重复观测只建一张卡`，
用真机原值 `1790733945898` / `1790734006291` 钉死该场景。

⚠️ **不是"算出来应该能红"，是真的红过**：

```
把 ORPHAN_DEDUP_WINDOW_MILLIS 临时改回 60_000L
  → 孤儿去重_真机实测60393毫秒… FAILED   （18 tests completed, 1 failed）
改回 90_000L
  → BUILD SUCCESSFUL，全量 411 / 0 failures
```

### ② 顺手发现原「超过 60 秒」负例会**假绿**

它原本用 `now + 90_000L` 当"窗口外"的值。窗口调到 90 秒后，该值**正好卡在边界上**
（`occurred_at BETWEEN ? AND ?` 两端闭区间 ⇒ 仍会去重）——**用它当负例，绿是假的**。

已改为 `now + 150_000L`：落在窗口外，且**仍在 D-6 的 2 分钟内**，
顺带证明了本窗口确实窄于 D-6。

## 六、附带发现：标签词时有时无（修正昨天的结论）

昨天的结论是「拼多多结算页标签词时有时无」。今天补到一条**更精确**的：

```
AmountDiag role=PAYMENT_RESULT nodes=320
  labeledTerms=[实付,订单金额,合计]  labeled=[]  unlabeled=[300,1850,500]  final=null
```

**三个标签词全在，`labeled` 却空。** 原因与原假设 A 描述的一致：**标签与金额分处不同节点**
（标签节点只有文字没数字，金额节点只有数字没标签）。

⇒ 修正为：**原假设 A 在结算页上不成立，但在结果页上成立。**
`CONFLICTS_2026-09-10.md` 的 C3 旁证说的是结算页，那部分对；结果页上标签确实存在，只是配不上对。

本次未造成问题——结果页金额走的是**微信**页面的 `PaymentResultParser`，与 PDD 的
`finalAmountMinor` 是两套通道。

## 七、踩的坑（今天新增 3 条）

11. ⚠️ **`settings put secure enabled_accessibility_services "<单个服务>"` 会抹掉用户其它无障碍服务。**
    本机列表有 5 个服务（小米AI阅读 / 支付宝 / GKD / omarea vtools / JotBill）。
    **昨天我这么写，等于替用户关了 4 个无障碍服务。**
    ⇒ 正确做法：**先读出完整列表、停进程、删文件、再把完整列表写回去**，
    由系统重绑自动拉起进程（这条昨天已踩，见下条）。
12. ⚠️ **无障碍重绑会*自动*拉起 App 进程**（昨天踩过，今天验证仍然成立）：
    "先启动 App 再删日志"是错的——`rm` 删掉的是刚建好的文件，进程句柄仍指向已删除的 inode，
    后续写入全进黑洞。现象：`init` 日志说"落盘已启用"，`ls` 却只有 dump 文件。
13. ⚠️ **`jotbill-dump.db` 只在 `Application.onCreate` 导出一次** —— 支付过程中不刷新。
    要看支付后的表内容必须重启 App。核对数据库时每轮都要重启，做 3 笔就重启了 3 次。

### 今天学到的两条方法论（记下来比代码值钱）

1. **定案值必须用它产生当天没覆盖到的场景再验一次。**
   昨天 D-25 定 60 秒时，每条依据都成立，但没有一条覆盖"用户在结果页停留超 60 秒"。
   而这恰恰是**最常见**的场景，不是边缘 case。
2. **三道防线共用阈值时，阈值会一起失效。**
   30s 桶 / 60s 记忆 / 60s 去重窗挤在同一窄带 ⇒ 任一场景超过 60 秒就全线失守。
   排查重复类问题时，**先把所有时间判据列出来看它们的阈值分布**，比逐个加日志快得多。
