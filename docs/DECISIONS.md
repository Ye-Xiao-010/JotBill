## 二、AI 服务商

| 决策项 | 确认值 | 说明 |
|---|---|---|
| 主用模型 | 通义千问 qwen-vl-plus | 质量优先,阶段一已验证 |
| 备用模型 | 智谱 GLM-4V-Flash | 主用故障或预算紧张时切换,阶段一已验证 |
| 开发调试模型 | 硅基流动 Qwen3-VL-8B-Instruct | 不作为生产识别模型,阶段一已验证 |
| API 格式兼容性 | 三家均兼容 OpenAI Vision 格式 | 阶段一已确认,无需多个适配器 |
| AI 月度成本预算默认值 | 10 元 | 用户可在设置中调整 |
| 连通性测试 | 设置页提供测试按钮 | 验证模型名称和 API 地址 |
| 模型下线处理 | 返回 AI_AUTH 错误码,提示用户检查 | 含连通性测试按钮 |

### 阶段一验证记录(2026-08-04)

| 原计划模型 | 问题 | 修正为 | 状态 |
|---|---|---|---|
| 智谱 GLM-4.7-Flash | 纯文本模型,不支持图片输入(错误码 1210) | GLM-4V-Flash(多模态) | ✅ 真机通过 |
| 硅基流动 Qwen2-VL-7B-Instruct | 7B 识别能力有限 | Qwen3-VL-8B-Instruct(8B,更优,仍免费) | ✅ 真机通过 |
| 通义千问 qwen-vl-plus | 无问题 | 保持不变 | ✅ 真机通过 |

**经验教训:** 模型命名相近但能力差异巨大(如 `glm-4.7-flash` vs `glm-4v-flash`),必须在适配器中硬编码默认模型名,并在文档中明确标注"不可误用"列表。后续新增服务商时,`AiProviderConfig` 需增加 `systemContentFormat: 'string' \| 'array'` 字段以避免硬编码修改。

## 三、识别与截图

| 决策项 | 确认值 | 说明 |
|---|---|---|
| 本地 OCR | 不使用 | 降级靠通知+待确认,减少 APK 体积 |
| 截图来源 | 自动检测 + 手动悬浮按钮 | 两者共存,共用 buffer |
| 悬浮按钮显示条件 | 购物APP前台就显示(方案A) | 用户可配置为"仅结算页显示"或"关闭" |
| 悬浮按钮覆盖规则 | 按时间戳保留最新 | 不区分手动/自动 |
| 手动截图后自动检测 | 同一页面指纹内不重复截图 | 避免用户刚点完又自动截一张 |
| 二维码检测 | 纯文本关键词判断 | 保守策略,可能漏检视觉二维码但更安全 |
| 截图上传时机 | 购买意图触发(提交订单/支付调起) | 结算页阶段只入内存 buffer |
| 快照过期 | 30 秒 | 过期后提交订单时若仍在结算页可补截一张 |

## 五、业务规则

| 决策项 | 确认值 | 说明 |
|---|---|---|
| 商户字段定位 | 场景相关字段,非必填 | 外卖/到店高价值,电商/出行低价值 |
| 优惠后金额差异 | AI ≥ 支付视为正常,不进待确认 | 只有 AI < 支付才是冲突 |
| 合并支付 | 已知限制,MVP 不自动拆分 | 进待确认由用户手动拆分 |
| 跨午夜时间口径 | 以 occurredAt 为准 | 不以通知到达时间为准 |
| 规则引擎执行时机 | 候选生成时 + 入账前都执行 | 两次都记录命中信息 |
| 规则作用于纯通知路径 | 是 | 通知识别也可由规则补全字段 |
| 预算超支提醒 | 80% 和 100% 各提醒一次 | 本地通知,可关闭 |
| 退款延迟关联 | 创建独立退款记录,提示手动关联 | 原交易过期/已删除时 |
| 退款到非原账户 | 以退款通知为准,不影响原交易关联 | 如微信支付退款到支付宝 |
| 押金入账 | 待确认弹窗提供"不计收支"选项 | 不应计为支出 |
| 支付失败会话 | 立即标记 FAILED/CANCELLED | 即使未过期,避免与新会话冲突 |

## 六、工程基线

| 决策项 | 确认值 | 说明 |
|---|---|---|
| 最低 Android 版本 | Android 13 (API 33) | 无障碍截图需 11+,定 13 兼顾覆盖率 |
| 真机测试基线 | 小米 17u,Android 16 | 主力调试机型 |
| 厂商兼容性首发 | AOSP/原生 + 小米 | 华为/OPPO/vivo 暂不提供针对性引导 |
| 数据库加密 | 默认 SQLCipher 加密 | 主密钥由 Keystore 派生 |
| 备份默认加密 | 默认不加密 | 用户可选加密,导出后用户自行负责 |
| 多账本/多用户 | 单账本 | 不支持多账本 |
| 审计日志保留 | 90 天 | 超期自动清理 |
| 数据库迁移失败 | 迁移前自动备份 + 失败回退 | 提示用户导出数据 |
| 应用升级机制 | 自发布 APK | 版本号管理、签名一致性、应用内检查更新 |
| 状态异常提醒 | 设置页显示 + 本地通知 | 无障碍/通知/AI 持续失败时通知 |

## 十、LiteNote 真实代码结构(调研结论)

基于 https://github.com/GystuG/LiteNote 实际抓取,与设计文档描述的差异:

| 项 | 设计文档描述 | 实际情况 | 处理 |
|---|---|---|---|
| 屏幕数量 | 18 个 | 24 个 .tsx 文件(含 reports 下 8 个 Tab/视图) | MIGRATION_MAP 按实际 24 个处理 |
| 状态管理 | 未明确 | MobX + React Query 5 同时使用 | 数据层迁移时两者都要改 |
| AI 集成 | 未明确 | 后端 NestJS 代理 4 家服务商,SSE 流式 | 去后端后 AI 要改为手机直连 |
| 原生模块 | 未明确 | 4 个:AuthToken/HotUpdate/PaymentNotification/InstallApk | 迁移时需评估每个模块去留 |
| 仓库结构 | 单项目 | Monorepo:litenote-mobile-app + litenote-backend | 迁移时路径前缀要调整 |
| 账户字段 | 设计文档新增了余额机制 | LiteNote 账户只有 balance 单字段,无期初/当前区分 | 类型定义按设计文档扩展 |
